# 구조 및 운영 전제

## 단일 원장

`lib/accounting.ts`는 DB와 UI에 의존하지 않는 정수 기반 회계 계산을 제공합니다. `lib/db.ts`가 SQLite 트랜잭션 경계와 저장을 담당합니다. 이 MVP는 사용자 거래와 분개를 `entries`에 1:1로 결합하고 각 차변·대변을 `lines`에 저장합니다. 취소는 별도 entry가 원 entry를 참조합니다. 보고서 합계를 따로 저장하지 않습니다. 개시분개는 운영성과에서 제외됩니다.

관계: years → entries → lines → accounts. financial_accounts → 고유 asset account. imports → bank_rows → bank_links → entries. budgets → year + account. rules → account. audits는 변경 전후를 보존합니다. 은행 원본과 분개·감사 이력의 UPDATE/DELETE는 트리거로 거절합니다. 상태 검사·분개 검증·은행 연결·감사 기록은 BEGIN IMMEDIATE 안에서 처리합니다. 균형 검증은 서비스 계층이 수행하므로 직접 SQLite 파일에 SQL을 실행하는 것은 지원하지 않습니다.

상위 계정은 집계용이며 직접 분개하지 않습니다. 과거 분개가 있던 계정을 상위로 바꾸는 구조 변경은 지원하지 않도록 제한해야 합니다. 원장 집계는 계정 유형을 사용하며 계정 유형 변경 API는 없습니다. 예산 중복 계층은 서버에서 거절합니다.

## 중복과 은행 원본

계좌·날짜·시간·정규화 금액·적요·잔액의 SHA-256 fingerprint를 반영 연결에 unique로 저장합니다. 파일을 반복 업로드해도 원본 행은 남고 두 번째 반영은 DB 제약으로 실패합니다. 같은 fingerprint를 갖는 합법적인 다른 거래는 자동으로 반영할 수 없으며 원본 확인 후 별도 수동 입력해야 합니다. 수동 입력과 은행 파일의 중복은 자동 판별할 수 없으므로 도입 시 기간을 분리해야 합니다.

## PC와 외부의 경계

PC 서버는 127.0.0.1에만 바인딩합니다. 로컬 요청의 Host/Origin과 cross-site 메타데이터를 검증합니다. OS 계정 접근자는 DB를 읽을 수 있습니다. 로컬 로그인/파일 암호화는 제공하지 않습니다.

외부 APP_MODE=viewer는 DB 조회 대신 Supabase Auth로 토큰을 검증하고 사용자 토큰으로 RLS가 적용된 사본만 읽습니다. Supabase 서비스 키는 PC 게시에만 사용합니다. HTTP 메서드 조작으로도 조회 배포의 변경 API를 사용할 수 없습니다. 렌더링된 HTML/JS에 키나 DB를 넣지 않습니다. Supabase anon key는 공개 가능한 식별자이며 RLS가 권한을 보호합니다. 별도 교회 여러 곳을 한 Supabase 프로젝트에 넣는 다중 조직 구조는 제공하지 않습니다.

## 마감 제안 — 미구현

사용자 승인 전에는 실제 마감을 실행하지 않습니다. 예정된 절차: 미분류/분개/대사 검사 → 일반분개 보고 확정 → 수익·비용을 순자산으로 대체하는 마감분개 → 자산·부채·순자산만 차기 개시분개 → 연도 잠금. 보고서에서는 마감분개를 구분해야 합니다. 차기연도 후속 거래 이후의 재개방은 별도 설계가 필요합니다.

## 배포 전 확인

- 실제 은행 샘플과 Google Sheets의 항목·금액·기초잔액 대사
- 회계 기준과 예산 집행 기준, 지정 목적 헌금 처리 승인
- 외부 공개 회원가입 비활성화 및 approved_viewers 설정
- 허용 사용자/비허용 사용자 각각 RLS 읽기 검사
- 외부 환경의 서비스 키 부재, PC 루프백 바인딩
- HTTPS, 세션 만료, 로그아웃, 다른 출처 요청 차단
- CSV/XLSX 수식 주입 방지, 업로드 크기/행 수 제한
- DB 백업 복구와 실제 계좌잔액 확인
- 패키지 보안 업데이트와 OS 접근 제어

금액과 계좌 자료는 민감하므로 외부 게시 버튼은 확인을 요구합니다. 외부 게시·인증은 실제 Supabase 자격증명과 배포 환경을 연결한 뒤 별도 검증해야 합니다.
